# Working on the Jali docs (apps/docs)

Read first: `docs/DOCS-PLAN.md` (what the site holds, and what is done), `CONTRIBUTING.md` (the checks, and how to write), `ARCHITECTURE.md`, `docs/research/docs-sites.md` (the direction), and the package's README (`packages/jali`).

## Run it

- `cd apps/docs && JALI_DOCS_CACHE=node_modules/.vite-<you> pnpm exec astro dev --port <your port> --ignore-lock`. Your own cache directory and port, always: two dev servers sharing a cache break each other. `--ignore-lock` keeps the server in the foreground (Astro starts it in the background when a coding agent runs it); strict ports come from astro.config.mjs, since Astro ignores `--strictPort`.
- Ports: 5400 lead, 5401 shell, 5402 live, 5403 concepts, 5404 reference, 5405 guides. The example apps' servers are 5300 (Data Studio) and 5350 (Loan review); leave them alone.
- The site is Astro (`astro.config.mjs`): `pnpm build` prerenders every page to static HTML in `dist/` (with sitemap, robots.txt and a `.md` copy of each page); a page that fails to prerender fails the build. Pages are static: the chrome, TOC and content are rendered at build time (`src/shell/render.tsx`, `src/shell/Shell.tsx`), code highlighted there. In the browser, `src/client/enhance.ts` runs the page tools (theme, copy, wrap, tabs and the install menu, TOC, drawer, search), each a `.client.ts` beside the component it works on, and only the live parts hydrate, as islands (`src/shell/island.tsx`, `src/client/islands.ts`), when they come near the screen. Live demos render in the browser only (`src/live/workspace/ClientOnly.tsx`). Measure with `node apps/docs/scripts/measure.mjs` against `astro preview`.
- `npx tsc --noEmit -p apps/docs` must pass. Check your pages in a real browser (Playwright, `channel: "chrome"`), at 1440 and 390 wide, light and dark.

## Contracts (names and props are fixed; implementations may change)

- **Pages** are MDX under `src/docs` (`src/pages` holds Astro's routes), path = URL (`learn/layout-tree.mdx` is `/learn/layout-tree`). Frontmatter: `title`, `summary` (one plain sentence), both required, and `layout` when the page isn't an ordinary one: `wide` (no column beside the page: the API reference), `showcase` (wide, and no "On this page": the Examples) or `landing` (the home page); `src/site/sources.ts` reads it and `src/shell/Shell.tsx` lays the page out. The nav is `src/site/nav.ts`; a path there without a page fails the build. The summary is also the page's meta description for search engines, so make it a sentence that stands alone. Don't repeat the title as an `# h1` in the page: the shell renders title and summary.
- **MDX components, available without import** (`src/shell/mdx/`, one file each): `<Code code lang filename highlight="3-5" />`, `<Callout type="note|tip|warning" title>`, `<Steps>` / `<Step title>`, `<Tabs group>` / `<Tab label>`, `<Install packages="…" />`, `<Cards>` / `<Card title href>`. Fenced code blocks also work (Shiki at build time, light and dark). They render static HTML: no hooks or state; what one does in the browser goes in a `.client.ts` beside it (run by `src/client/enhance.ts`), and finds it by its data attributes. Tabs and install lines are choice groups (`src/shell/mdx/choice.client.ts`).
- **Live parts** (`import { TreeView, Frame, Spotlight, QuickstartApp, Hero } from "../../live"`), each an island, so their props must be JSON (strings, numbers, booleans): `<QuickstartApp height caption />` (the Quickstart's notes app), `<TreeView layout panels height caption showJson detail tries />`, `<Frame layout width minWidth height caption />`, `<Spotlight layout target height caption />`, `<Hero layout height />` (the home page only). `layout` is a layout id from `src/live/shop/layouts.ts` (`two`, `chain`, `desk`, `nested`, `stack`, `strip`, `crowded`, `board`); `target` is `shelf`, `follow`, `drop-zones`, `tabs`, `divider` or a selector.
  - TreeView `panels` says what sits beside the live panes: `auto` (the default: map and JSON side by side when wide, else a Map | JSON switch, `showJson` starting on the JSON), `map`, `json` or `map+json`. `detail` shows sizes and the overlay card, for pages that teach the model. `tries={false}` drops the row of things to try.
  - Hero is the home page's: the panes with one closable panel beside them (map, JSON or both) and the scripted tour (`src/live/hero/tour/story.ts`).
  - Inside `src/live`: `shop/` is the example app (data, one file per pane with its kind, layouts, `open.ts`), `workspace/` hosts it in a figure (`jali-gaps.ts` holds what Jali's public API doesn't give yet, each recorded in `src/live/FINDINGS.md`), `tree/` draws the layout tree, `figures/` are the parts pages use, `hero/` is the hero and its tour. Each part's CSS sits beside it; `live.css` imports them after `type.css`, the live parts' type scale.
- **The Markdown copies** ("View as Markdown", the `.md` pages, `/llms-full.txt`, the package's `docs/`) are made by `src/site/markdown`, which parses each page with the site's MDX compiler and writes each component as the Markdown its area gives it: `src/shell/mdx/markdown.ts`, `src/reference/markdown.ts`, `src/examples/markdown.ts`, `src/landing/markdown.ts`, and one line for every live part. A component with no entry there is dropped and its text kept. A new island needs its name in `src/client/island-id.ts`, where its loader (`src/client/islands.ts`) and its Markdown line are checked against it. Generated tables draw their rows from their data module (`command-data.ts`, `token-data.ts`, `parts-data.ts`), once for the page and once for the Markdown. After a change that touches them, `pnpm agent-docs` rewrites the package's copies.
- **Never write multi-line code inline as `<Code code={`…`} />`:** MDX strips each line's leading spaces. Use a fenced block (```tsx filename="src/x.tsx" highlight="3-5") or a `?raw` sample file.
- **A summary containing ": " must be quoted** in the frontmatter, or the page fails to build.
- **Code samples that must stay true** live as real `.tsx` files under `src/samples/<area>/` and are shown with `import code from "../../samples/…/x.tsx?raw"` and `<Code code={code} … />`. The typecheck covers them, so a sample that no longer matches the packages fails the build.
- **Short fenced blocks are typechecked too**, by `pnpm docs-check` (`tooling/docs-check.mjs`): each `ts and `tsx block is compiled as a module, with the names in `src/samples/prelude.d.ts` in scope and relative imports (`./panes`) resolved to `src/samples/app.ts`. A block that can't stand alone says `nocheck` in its meta. The same check compares every `<Params>` table in the reference with the type it documents.

## Writing

- Plain, short sentences. Say what something does for the reader, then how. Say "Jali", "panes" and "the layout" for what a person sees and "the instance" for what `createJali` returns; never "workspace" in prose. A curated page's modes are "Single view" and "Split view"; the phone layout is "one pane at a time". British spelling. One idea per paragraph. No marketing words ("powerful", "seamless", "robust"), no em dashes, no jargon a reader has to look up; when a Jali word is needed, link it to Key concepts the first time.
- Every fact about behaviour comes from the code (`packages/core/src`, `packages/react/src`) or the repo's tests and decisions (`docs/DECISIONS.md`). Don't guess. If you can't confirm something, leave it out and say so in your report.
- Examples use neutral, real-feeling domains (orders, customers, notes, tickets), never "foo/bar".
