A workspace's behaviour lives in the workspace, not in its components. So most of it can be tested without rendering anything: make a workspace, run actions on it, and read its state. This guide uses Vitest with jsdom; any test runner works the same way.

## A workspace for tests

<Code code={test} filename="src/workspace.test.ts" highlight="7-19" />

Each option keeps the test apart from the page and from other tests:

- **`url: { location: memoryLocation(search) }`** is an address in memory. The workspace writes its layout there instead of the browser's address. Start it with a search string to test opening a link.
- **`storage: memoryStorage()`** keeps saved settings, pane state and dragged sizes in memory, never in `localStorage`.
- **`size`** gives the workspace a size. Folding depends on it, and with no rendered workspace nothing measures the window. Change it later with `workspace.set({ area })`.
- **`moveFocus: false`** stops the workspace moving DOM focus into panes after changes. There are no panes in the DOM in a workspace test.

Kinds belong to the workspace, so every test gets its own: nothing about one workspace affects another.

## Run actions, read state

`workspace.actions` holds every workspace action: `openBeside`, `close`, `preset`, `select`, `setUnsaved` and the rest. Components call the same actions, so a test that runs them tests what a person does.

- `workspace.get()` is the state: `layout`, `view.focused`, `confirm` (a held change waiting for "Discard unsaved changes?"), `unsaved`, `paneState`, `selection`.
- `workspace.model()` is what is derived from it: `panes` in tree order, `pane(id)`, `folded`, `visible`, `resolved` (every pane's box on screen).

An action that opens a pane returns its id.

## Test a link

To check that a link opens what it should, make a second workspace whose `memoryLocation` starts at the first one's address. A workspace reads its address when it is made, as a page load does:

```ts
const { workspace: reader } = testWorkspace(link);
expect(ids(reader)).toEqual(ids(workspace));
```

`memoryLocation` also records history. `location.entries` lists every entry, so you can check which changes push a new one. `location.visit(search)` acts like Back, Forward or a router link: the address changes and a started workspace hears it.

## Timing

Some changes wait. A following detail shows the list's item once the cursor rests (150ms), and divider sizes reach the address 120ms after the drag. Use fake timers and move them on:

```ts
vi.useFakeTimers();
workspace.actions.select("orders", orderKind({ id: 5 }));
vi.advanceTimersByTime(200);
expect(workspace.model().pane("order")?.ref.params.id).toBe(5);
```

## Keys

`workspace.start()` listens on the window, so a test can fire `keydown` events at an element and check what the workspace did. Pass `keymapOptions: { platform: "mac" }` (or `"other"`) so the test means the same keys on every machine. Call the function `start` returns to remove the listeners after the test.

## What to test in the browser

Store tests cover rules: what opens where, what folds, what asks first. Test the rest in a real browser, with Playwright or similar: that your components render, that dragging works, and how things look.
